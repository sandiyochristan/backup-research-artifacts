Wear OS Security Research: Threat Model and Attack Vectors Reference

Wear OS vs Android — unique attack surface

Wear OS exclusives
  • Tiles API (watch face panels)
  • Complications (data widgets)
  • Health Services API
  • Wearable Data Layer (channel to phone)
  • Watch Face Format (WFF) XML
  • Ongoing Activity API
  • Ambient mode & always-on display
  • Rotary input / bezel events
Shared with Android
  • Intent / Binder IPC model
  • Permission framework
  • ContentProvider / BroadcastReceiver
  • ADB shell access
  • SELinux enforcement
  • Keystore / StrongBox
  • Bluetooth & NFC stack
  • WebView (limited)

Key differences that widen the attack surface

Gap Many Wear OS apps are companion-free or receive data from a paired phone via the Data Layer API — a second trust boundary most Android researchers ignore.
Gap Tiles run in a separate process with no full Activity lifecycle, making intent-confirmation UX patterns from Android phone apps hard to replicate — as proven by CVE-2025-12080.
Gap Health Services runs as a privileged system service. Its permission model for heart rate, ECG, SpO2, and body temperature data is still maturing vs. Android's HEALTH_CONNECT.
Wear The Wearable Data Layer (MessageClient, DataClient, ChannelClient) tunnels data over BLE to/from the paired phone — a lateral movement path back to a full Android device.
Android Standard Android has a much richer ecosystem of security tooling. Wear OS is under-tested, so well-known Android bug classes often have unpatched equivalents on Wear.

Tooling for Wear OS research

ADB over BT / WiFi
Connect to Pixel Watch via adb connect over paired Bluetooth or Wi-Fi. Enables logcat, shell, dumpsys, am/pm commands identical to Android.
Setup first
drozer (Wear APK)
Side-load the drozer agent APK onto the watch. Run attack modules for exported components, intent fuzzing, content providers — same flow as phone testing.
IPC testing
Frida
Push frida-server ARM64 binary to the watch. Hook Wear OS system services, Health Services API calls, or Data Layer message handlers at runtime.
Dynamic analysis
jadx / apktool
Pull Wear APKs via adb pull. Decompile with jadx to review intent filter configs, exported flags, and permission declarations in AndroidManifest.
Static analysis
Burp Suite + Proxy
Route watch HTTP/S traffic through a laptop proxy by setting up Wi-Fi with a custom CA cert. Useful for companion cloud API calls made from the watch.
Traffic analysis
Wireshark + nRF Sniffer
Capture BLE GATT traffic between watch and phone using an nRF52840 dongle + Wireshark. Critical for Data Layer and BT pairing research.
BLE sniffing
Custom Wear PoC app
Build a minimal Wear OS app with Tiles/Complications support. Use it as the malicious app in your attacker model — no special permissions needed.
PoC
Android Emulator (Wear)
Android Studio includes Pixel Watch 2 AVDs. Good for rapid iteration on static analysis findings before testing on hardware.
Emulation

Reporting to Google MVRP

1
Reproduce on latest patch level
Always test on the latest Wear OS build. Check Settings → System → About → Software version. Google won't reward issues fixed in a prior bulletin.
2
Build a minimal PoC APK
Create the simplest possible app that demonstrates the issue. No third-party SDKs. Include full source code in the report — reviewers will build and test it.
3
Screen-record the attack
Use adb shell screenrecord on the watch and screen mirroring on the phone side. A 30-second video demonstrating impact dramatically speeds up triage.
4
Submit via Google MVRP
File at g.co/vulnz. Choose "Android & Google Devices". Include device model, OS/patch level, affected component, CWE, CVSS score, and full reproduction steps.
5
90-day disclosure window
Google typically targets a 90-day fix. The Wear OS Security Bulletin publishes monthly — expect your CVE in the next bulletin after the fix lands.
